# Project Style Guidelines and Behavioral Rules

## Rule 1: No Emojis or Decorative Symbols
- Do NOT use emojis, pictorial symbols, colored boxes, or decorative glyphs in any documentation, source code, commit messages, logs, or comments.
- Keep all documentation and code clean, minimal, and strictly professional (Standard ASCII / Plain Markdown).
- Use standard markdown headers (`#`, `##`, `###`), standard lists (`-`, `*`, `1.`), and standard tables for formatting.

## Rule 2: Documentation Language
- All official project documentation (e.g., `README.md`, architecture docs, API references) intended for the repository MUST be written in professional, clear, and idiomatic English.

## Rule 3: Clean Engineering Tone
- Use factual, precise technical language.
- Avoid marketing fluff, decorative icons, and unnecessary formatting flourishes.

## Rule 4: Planning and Autonomous Execution
- When given a task, present a structured implementation plan outlining: objectives, files affected, technical approach, and verification steps.
- Wait for user feedback or approval.
- Once approved by the user, execute all steps autonomously to completion without requesting redundant micro-confirmations.
- Run tests and deliver the final result upon completion.
